# دليل النشر والاستعادة الآمنة

التقييم الحالي: الفرع جاهز للاختبار فقط. الإنتاج الحالي غير معتمد؛ توجد أخطاء تلف قاعدة بيانات في سجلاته وكشف ملفات عامة. لا تنفذ الخطوات التي تغيّر Production قبل المراجعة والموافقة.

## 1. قبل المساس بخدمة الإنتاج

1. احتفظ بتعريف النشر الحالي وCommit ونسخة إعداداته. لا تضغط Restart أو Redeploy الآن.
2. استخرج نسخة متسقة من قاعدة الإنتاج وملفات المشاريع والمرفقات عبر قناة إدارية محمية. لا تستخدم رابط SQLite العام.
3. إذا فشل SQLite backup بسبب التلف، احتفظ بملفات DB وWAL وSHM معاً، وتوقف عن الاستبدال. يلزم استرداد منفصل ومقارنة السجلات والمجاميع؛ لا تستخدم Seed ولا تستبدلها بقاعدة محلية لمجرد أنها تفتح.
4. افحص integrity_check وforeign_key_check وتوازن كل قيد، وطابق أعداد المستندات والأرصدة والتقارير قبل/بعد الاسترداد. لم تُنجز هذه الخطوة على بيانات الإنتاج بعد.
5. دوّر كلمات المرور والـPIN الافتراضية قبل الاعتماد. رموز الطوارئ المنشورة أزيلت، ولن يقبل الخادم PIN افتراضياً معروفاً في بيئات staging/production.
6. دوّر مفاتيح JWT المستقلة. هذا ينهي الجلسات القديمة ويستلزم تسجيل الدخول مجدداً.
7. لا تغيّر BANK_ENCRYPTION_KEY مباشرة عند وجود بيانات بنكية مشفرة. استخدم أداة النسخ وإعادة التشفير أدناه أولاً.

## 2. دورة العمل

الفرع railway-security-readiness → CI واختبارات معزولة → بيئة staging داخل المشروع القائم ببيانات منفصلة → مراجعة نتائج التجربة → موافقة الإنتاج → نشر من main.

لا يُعاد ربط خدمة الإنتاج بفرع الاختبار. لا تُنسخ أسرار الإنتاج إلى ملفات Git أو إلى حسابات الاختبار.

## 3. إعداد الخدمة المستهدف بعد الموافقة

| الإعداد | القيمة المطلوبة |
|---|---|
| المستودع | mrmatreix/rawasi-aden |
| Root Directory | جذر المستودع |
| البناء | Dockerfile؛ ينفذ npm ci ثم npm run build داخل مرحلة البناء |
| Node | 24.x بحسب engines؛ صورة node:24-bookworm-slim |
| التشغيل | npm start |
| عنوان الاستماع | 0.0.0.0 وPORT الذي توفره Railway |
| قاعدة البيانات | SQLite حالياً؛ لا يعتمد MySQL قبل اختبار مستقل |
| Volume | /data، منفصل عن /app، مع صلاحية الكتابة للمستخدم node داخل الصورة |
| النسخ | واحدة؛ WEB_CONCURRENCY=1 |
| Readiness | /api/ready، مهلة نشر 120 ثانية مقترحة |
| Restart | On Failure، خمس محاولات مقترحة |
| إيقاف الخدمة | SIGTERM يوقف استقبال الطلبات ويغلق قاعدة البيانات؛ مهلة إنهاء مناسبة لا تقل عن 15 ثانية |
| HTTPS | النطاق الحالي؛ تحقق من الشهادة والاتصال بعد النشر |
| CI | إبقاء Wait for CI مفعّلاً وجعل الاختبار الحرج مطلوباً في حماية main |

Railway أوقفت اعتماد Config as Code للخدمات الجديدة؛ لا تعتمد على مجرد إضافة railway.json. استخدم إعدادات اللوحة المعتمدة أو استورد التعريف الحالي بـ `railway config pull` ثم راجع `railway config plan` دون تطبيق. لا تنفذ apply أو migrate --apply قبل الموافقة. [المصدر](https://docs.railway.com/infrastructure-as-code).

### متغيرات البيئة

```dotenv
NODE_ENV=production
DB_ENGINE=sqlite
RAWASI_DATA_DIR=/data
RAWASI_DB_PATH=/data/rawasi_aden.db
RAWASI_UPLOAD_DIR=/data/uploads
RAWASI_PROJECTS_DIR=/data/projects
RAWASI_BACKUP_DIR=/data/backups
RAWASI_SCRATCH_DIR=/data/scratch
WEB_CONCURRENCY=1
ENABLE_SCHEDULERS=true
```

اضبط JWT_SECRET وCLIENT_JWT_SECRET وBANK_ENCRYPTION_KEY في لوحة الأسرار، بقيم مستقلة عشوائية لا تقل عن 32 حرفاً. لا تحفظها في Git أو التقرير. أضف أصول الويب وتطبيق Android المصرح بها في CORS_ORIGINS؛ اختبرها فعلياً. لا تضع origins عامة أو wildcard.

قاعدة SQLite الموجودة والمفحوصة يجب أن تُنقل إلى Volume قبل تشغيل النسخة الجديدة. الخادم يرفض البدء إذا غابت القاعدة أو الأسرار أو كانت المسارات داخل حزمة التطبيق. غياب البيانات لا يؤدي لإنشاء مستخدمين أو مشاريع تجريبية.

في staging استخدم NODE_ENV=staging وأسراراً وقاعدة وVolume مستقلين، مع ENABLE_SCHEDULERS=false أثناء التجارب. أمر npm run start:staging لا يستنسخ الإنتاج تلقائياً.

## 4. الاختبار قبل الاعتماد

```sh
npm ci --ignore-scripts
npm run build
npm test
npm audit --omit=dev --audit-level=high
```

npm test ينشئ بيانات اصطناعية مؤقتة، ويختبر الحفظ والترحيل والتقارير والملفات والصلاحيات والاستعادة. لا يقرأ قاعدة العميل الفعلية. الاختبارات القديمة الأخرى ليست شهادة لتغطية كل وظائف المشاريع والموارد البشرية والمخزون، ولا تشغّلها على قاعدة حقيقية.

CI يتضمن كذلك بناء Docker وتشغيله على بيانات اصطناعية وVolume محلي في عامل CI، ثم فحص الجاهزية ووقفه وإعادة تشغيله. لا يثبت ذلك نجاح Volume داخل Railway.

بعد نشر staging فعلياً: أنشئ صرفاً وقبضاً وقيداً ومرفقاً، تحقق من حساباتها ومركز التكلفة وعدم تكرار الترحيل، ثم Restart وRedeploy وقارن الأرقام والمرفقات والتقارير. اختبر الأدوار ونطاقات المشاريع وتطبيق Android وWebSocket. اختبر فشل قاعدة البيانات والتخزين، وفشل readiness، وخطة Rollback.

## 5. النسخ الاحتياطي

- الجدولة تستخدم الحزمة الكاملة: قاعدة SQLite عبر native backup، ملفات المشاريع والمرفقات، manifest وبصمات الملفات. لا تعتمد على نسخ DB وحده أثناء WAL.
- النسخ في /data/backups محمية بصلاحية settings:backup. راجع آخر نجاح وفشل من شاشة النسخ وسجل التدقيق.
- نسخة على Volume نفسه لا تكفي كنسخة خارجية. مزامنة cloud_vault أو مجلد محلي لا تثبت نسخة مستقلة خارج Railway.
- يلزم اعتماد وجهة خارجية مشفرة واختبار إرسال نسخة واسترجاعها، ثم مراقبة فشل الإرسال. هذه الخطوة لم تُختبر بعد.
- راجع الاحتفاظ من إعدادات المحرك وكمية الملفات؛ ضع إنذاراً لامتلاء القرص، وآخر نسخة ناجحة، وفشل readiness. لم تُفعّل مراقبة خارجية أو تكلفة إضافية في هذه المهمة.

## 6. استعادة معزولة قابلة للفحص

للحزم غير المشفرة الصادرة من محرك النسخ الموحد:

```sh
node scripts/restore_bundle.js verified-bundle.zip NEW_EMPTY_RESTORE_DIRECTORY
```

الوجهة يجب ألا تكون موجودة. الأداة تفحص مسارات الأرشيف والحجم والبصمة وSQLite والعلاقات وتوازن القيود، ثم تستعيد القاعدة والمشاريع والمرفقات. حد الأرشيف المفكوك 512 MB؛ لا ترفعه دون مراجعة سعة الذاكرة. لا تستعيد الأداة فوق النظام العامل.

للحزم المشفرة: افحصها وفكها عبر آلية المحرك المعتمدة في بيئة منفصلة مع إبقاء كلمة المرور خارج Git والسجلات. أداة restore_bundle لا تفك التشفير بذاتها، ولا تدعم كل صيغ الخزنة القديمة.

شغّل النسخة المستعادة بمعطيات مستقلة، وطابق المستخدمين والمشاريع والقيود والتقارير وبصمات المستندات. اختُبر هذا محلياً ببيانات اصطناعية؛ إنتاج Railway لم يُستعد بعد.

## 7. تدوير مفتاح بيانات البنوك دون تعديل الأصل

مرّر OLD_BANK_ENCRYPTION_KEY وBANK_ENCRYPTION_KEY عبر البيئة الآمنة، ثم:

```sh
node scripts/rotate_bank_key.js VERIFIED_SOURCE.db NEW_ROTATED.db
```

تُنشأ قاعدة جديدة؛ يفشل العمل إذا كانت الوجهة موجودة أو تعذر فك أي سجل. يُختبر فتح البيانات بالمفتاح الجديد قبل اعتماد القاعدة الجديدة. احتفظ بالمفتاح القديم والنسخة الأصلية حتى نهاية اختبار الرجوع. لا تطبع المفاتيح في الأوامر أو السجلات أو الدردشة.

## 8. الرجوع عن النشر

1. جمّد الكتابة في نافذة صيانة معتمدة وخذ حزمة سلامة متسقة.
2. ارجع إلى Commit والصورة المعتمدين سابقاً. لا تفترض أن إرجاع الكود يعيد القاعدة أو يزيل ترحيلات المخطط.
3. إذا كان الرجوع يحتاج بيانات، استعد الحزمة إلى وجهة جديدة وافحصها أولاً؛ لا تستبدل DB/WAL للنظام أثناء تشغيله.
4. بعد إيقاف الخدمة بصورة منظمة، اعتمد القاعدة والمرفقات المتطابقة كمجموعة واحدة، مع إبقاء المجموعة السابقة للرجوع.
5. طابق أرصدة الحسابات وأعداد السندات وبصمات الملفات، واختبر readiness والحفظ والترحيل قبل فتح الخدمة.

خطوات الرجوع موثقة ولم تنفذ على الإنتاج. لا يُعتمد النظام حتى نجاح تجربة staging الفعلية، وفحص قاعدة الإنتاج واستعادة نسخة منها، وتطبيق إغلاق المسارات المكشوفة وتدوير الأسرار.
