# Rawasi — الهيكلة وقاعدة البيانات وطبقة المجال

هذه مساحة عمل مستقلة عن نظام رواسي الحالي. لم يُطبق الترحيل على قاعدة بيانات الموقع ولم تُنشر هذه الملفات. يشمل العمل الجديد الهيكلة والمخطط والترحيل وطبقة المجال المستقلة واختباراتها؛ ملفات `backend/src/orders` القديمة نموذج أولي سابق غير متصل بالنظام، وتستخدم أسماء أدوار قديمة ولا تعد تنفيذًا للمرحلة التالية.

## الهيكلة

```text
rawasi-platform/
├── backend/
│   ├── prisma/
│   │   ├── schema.prisma
│   │   └── migrations/20261114000000_initial/migration.sql
│   ├── src/
│   │   ├── shared/{domain,data,presentation}/
│   │   ├── features/
│   │   │   ├── identity/{domain,data,presentation}/
│   │   │   ├── catalog/{domain,data,presentation}/
│   │   │   ├── vendors/{domain,data,presentation}/
│   │   │   ├── orders/{domain,data,presentation}/
│   │   │   └── inventory/{domain,data,presentation}/
│   │   └── orders/                       # نموذج أولي سابق مستقل
│   ├── tests/
│   └── package.json
├── web/src/
│   ├── app/                             # Next.js App Router عند تنفيذ الواجهة
│   └── features/{identity,catalog,vendors,orders,inventory}/{domain,data,presentation}/
└── mobile/lib/
    ├── app/
    └── features/{identity,catalog,vendors,orders,inventory}/{domain,data,presentation}/
```

المجلدات الفارغة تحدد أماكن الوحدات المستقبلية وليست تطبيقات قابلة للتشغيل. `domain` لنماذج وقواعد العمل، و`data` للتخزين والتكامل، و`presentation` لواجهات الاستخدام أو نقاط الاتصال.

## القرارات والقيود

- الأدوار الأربعة محفوظة في `RoleCode`، وربط الصلاحيات بالأدوار في `role_permissions`. لا تمنح قاعدة البيانات الصلاحيات تلقائيًا؛ يجب إنفاذها في المصادقة والواجهة الخادمية عند تنفيذها.
- `hideInitialPrice` افتراضيًا صحيح، و`allowClientBudget` افتراضيًا خطأ. الهامش في `rawasiMarkupPercent` كسر عشري: 0.3000 يعني 30%، والعملة رمز من ثلاثة أحرف. الحقول الداخلية والمرئية مفصولة لكن عزلها في الاستجابات يحتاج API ذات قوائم سماح وصلاحيات، ولم يُنفذ هنا.
- مدة العقد مقيدة بسنتين إلى خمس سنوات. سجل التقييم الربعي يسمح بدرجة أقل من 4 لتمكين تسجيل النتائج المنخفضة؛ إصدار التنبيه يحتاج مهمة مستقبلية. عدد العمال مستنتج من السجلات النشطة وليس قيمة مكررة. مواعيد SLA موجودة لكن لا توجد تنبيهات أو حسابات تلقائية.
- رقم عضوية وتواريخ إصدار البطاقة محفوظة دون كلمات مرور أو رموز مؤقتة قابلة للطباعة في قاعدة البيانات. صور بطاقات العمال تخزن كمفاتيح خاصة، ولا بد من تخزينها وعرضها بمصادقة لاحقًا.
- قيد العلاقة المركبة يمنع اختيار عامل يتبع منفذًا آخر. يتحقق محرك قاعدة البيانات عند تسجيل العهدة أن المنفذ هو المنفذ المعين للطلب وأن عقده عمل يد فقط. لا تتضمن هذه المرحلة محرك أرصدة المخزون أو سياسات منع تغيير العقد أو تغيير تعيين الطلب بعد صرف عهدة؛ يجب معالجتها قبل تشغيل العهدة.
- الحذف الناعم لا يعيد استخدام رموز المستخدمين والعضويات والأسعار الفريدة. حقول `createdById` و`updatedById` تحفظ معرّف الفاعل لكنها ليست مفاتيح خارجية عامة؛ سجل انتقالات الطلب يربط الفاعل بمفتاح خارجي. تغير صلاحيات المستخدمين وصحة تطابق الدور مع ملفات العميل أو المنفذ، وتطابق نطاق المنفذ والمنطقة والخدمة، يجب فرضه في الخدمات ومعاملاتها لاحقًا.
- يعتمد `uuid()` و`updatedAt` في Prisma على العميل؛ الإدخال المباشر عبر SQL يجب أن يوفّر قيمهما. لا يتضمن هذا المخطط تحويل بيانات النظام الحالي أو نشرها.

## التحقق

بعد تثبيت تبعيات مجلد `backend`، نفذ `npm run schema:validate` مع متغير `DATABASE_URL` لعنوان PostgreSQL، و`npm run schema:test` لاختبار الترحيل المعزول بـ PGlite. يتطلب النشر الفعلي اختبار الترحيل على إصدار PostgreSQL المستهدف، ومراجعة أمان وعزل البيانات وخطة ترحيل بيانات النظام الحالي.

## المرحلة الثانية: طبقة المجال

توجد قواعد التسعير والحالات وعزل الاستجابات في `backend/src/features/orders/domain/`، واختباراتها في `backend/tests/core-domain.test.ts`. جميع المبالغ نصوص عشرية بدقتين، وتحسب بوحدات صحيحة؛ النسبة المدخلة كنسبة مئوية (30 تعني 30%)، بينما نسبة المخطط العشرية (0.3000 تعني 30%)، وعلى طبقة التخزين تحويلها بدقة. تعتمد قواعد ظهور سعر العميل على قيمة قسم الخدمة وعلم الميزانية وعلم تشغيل الميزة.

القواعد مستقلة ولا تطبق مصادقة أو تحفظ بيانات أو ترسل إشعارات. يجب على طبقة التطبيق التحقق من هوية المستخدم وقراءة سقف الأسعار والعامل والتصنيف من مصدر موثوق، ثم حفظ تغيير الحالة والتدقيق والتقييم الربعي بذات المعاملة وتطبيق التحكم في التزامن. دالة SLA تحسب الاستحقاق ولا تشغل مؤقتًا. التقييم الربعي يحسب تجميعة من تقييمات المدة المقدمة إليه ولا يحفظها. الأوصاف وملاحظات البنود المعروضة للعميل يجب أن تكون بيانات صالحة للنشر؛ لا يمكن للتصفية التلقائية ضمان خلو النص الحر من معلومات حساسة. قبل الربط يجب إضافة تخزين منفصل للأوصاف المخصصة للعميل وأسباب تعديل التكلفة وبيانات الموافقة وملاحظات العميل عند الحاجة، مع ربط قيم الحالات بنموذج البيانات.

بعد `npm ci` داخل `backend`، شغّل `npm run domain:test` و`npm run domain:typecheck`. اختبارات PGlite لا تغني عن اختبار PostgreSQL الهدف ولا يوجد نشر للموقع في هذه المرحلة.

## المرحلة الثالثة: العمل الجاري

أضيف حارس `SupervisorScopeGuard` كطبقة تطبيق مستقلة عن إطار الويب. يعتمد على مستخدم تمت مصادقته مسبقًا ومستودع موثوق، ويتحقق من نشاط المستخدم والعقد والتعيين والمنطقة والقسم. لم يُربط بمصادقة JWT أو بحارس NestJS أو بمستودع Prisma بعد؛ يجب قراءة بيانات التفويض وإعادة التحقق داخل معاملة العملية لتجنب تغيرها بين التحقق والتنفيذ. تاريخ العقد يقارن بتوقيت عدن.

أضيف `IssueCustodyUseCase` باستخدام واجهة معاملة قابلة للاستبدال: يخصم الرصيد بتحديث مشروط ويسجل العهدة في المعاملة نفسها، ويعتمد على قيد قاعدة البيانات للتحقق من المنفذ والطلب ونوع العقد. اختُبرت المعاملة والتراجع والطلبات المتزامنة في PGlite المعزولة، ولا توجد حتى الآن وصلة PostgreSQL إنتاجية أو REST API أو سياسات لاستلام المخزون وتسوية العهدة أو مصادقة فعلية. لا تُشغّل المكونات بوصفها نظامًا إنتاجيًا قبل تنفيذ هذه الطبقات واختبارها على PostgreSQL.

واجهات الطلبات والتسعير، وتسجيل المنفذين ورفع الصور الآمن، وفتح حسابات الشركات وتوليد بيانات الدخول، وحفظ الإشعارات وSLA لم تنفذ بعد. المخطط الأولي ما زال محليًا وغير مطبق ويجب ترحيله ومراجعته قبل الاستخدام.
